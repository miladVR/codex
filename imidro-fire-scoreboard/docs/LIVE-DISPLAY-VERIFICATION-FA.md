# اصلاح قرعه، تابلو دوم و رتبه‌بندی زنده

## ۱. تحلیل خطا و حدود نتیجه‌گیری

پشتهٔ پروژه Electron است؛ انتقال تصویر از یک وب‌سرور انجام نمی‌شود. پنجرهٔ عمومی HTML محلی را می‌خواند و state را با IPC دریافت می‌کند.

ضعف‌های مشخص مسیر قبلی:

- handler بازکردن پنجره قبل از اتمام `loadFile` پاسخ موفق می‌داد؛ خطای load به دکمه و اپراتور برنمی‌گشت.
- اگر پنجره موجود بود، فقط focus می‌شد؛ اتصال یا تغییر مانیتور مقصد باعث جای‌گذاری مجدد نمی‌شد.
- مقصد همیشه اولین مانیتور غیر اصلی بود؛ انتخاب مانیتور و گزارش وضعیت/خطا وجود نداشت.
- ارسال state هنگام بارگذاری کنترل نشده بود؛ استعلام اولیه و رویداد می‌توانستند بدون revision با یکدیگر رقابت کنند.
- اعلان‌ها فقط نتیجهٔ approved تازه را می‌دیدند؛ draft و ویرایش فوری مطابق درخواست جدید منتشر نمی‌شدند.

راهکار در [کنترلر نمایشگر](../display-controller.cjs): انتظار واقعی برای load، ارسال state پس از `did-finish-load`، بازجای‌گذاری پنجرهٔ موجود، رسیدگی به display-added/removed/metrics-changed، انتخاب مقصد، غیرفعال‌کردن background throttling و یک تلاش reload در صورت توقف renderer. رابط خطا را نمایش می‌دهد. `revision` مانع بازگشت به state قدیمی است و استعلام هر پنج ثانیه برای بازیابی رویداد ازدست‌رفته استفاده می‌شود؛ مسیر اصلی همچنان push فوری IPC است.

**این موارد ضعف‌های کد و سناریوهای آزموده‌شده‌اند؛ علت قطعی خرابی ویدئوال فیزیکی کاربر بدون تست HDMI/تنظیمات ویندوز قابل اثبات نیست.** Mirror در برنامه «پیش‌نمایش همان صفحهٔ سالن روی نمایشگر اصلی» است، نه تغییر Duplicate سیستم‌عامل یا آینه‌کردن پنل حاوی داده‌های داوری. برای جداسازی واقعی، Win+P → Extend لازم است. برنامه تنظیمات سیستم را تغییر نمی‌دهد.

| بخش | فایل |

| ترتیب اجرای ثابت و sort علمی/زمانی، رسمی و موقت | [scoring.cjs](../scoring.cjs) |
| پنجرهٔ دوم، آماده‌شدن، broadcast و کنترل فرستنده | [display-controller.cjs](../display-controller.cjs) |
| اتصال production و قفل تک‌نمونه‌ای برنامه | [main.cjs](../main.cjs) |
| API renderer | [preload.cjs](../preload.cjs) |
| فرم نوبت دستی و انتخاب تابلو هر رشته | [admin.js](../src/admin.js) |
| تابلو کل/آیتم/قرعه، شماره آبی و رتبه طلایی، هایلایت | [display.js](../src/display.js) |

```js
// تمام تیم‌ها باید یک بار و همهٔ اعداد 1..N باید یکتا باشند.
await scoreboardAPI.createDraw({
  disciplineId: "all", // یا water, combined, scientific, rescue_skill, height
  method: "manual",
  entries: [{ teamId: 1, drawOrder: 2 }, { teamId: 2, drawOrder: 1 }]
});
await scoreboardAPI.createDraw({ disciplineId: "water", method: "auto" });
// جایگزینی پیش از شروع: replaceDrawId باید UUID آخرین قرعهٔ همان محدوده باشد.

await scoreboardAPI.setDisplay({ mode: "item", disciplineId: "water" });
await scoreboardAPI.setDisplay({ mode: "standings" });
await scoreboardAPI.setDisplay({ mode: "draw", drawId: "UUID" });
await scoreboardAPI.openDisplay({ mode: "extend", displayId: 123 });
await scoreboardAPI.openDisplay({ mode: "mirror" });
await scoreboardAPI.closeDisplay();
const status = await scoreboardAPI.getDisplayStatus();
// status: { open, mode, targetId, error, displays: [{id, primary, label, bounds}] }
```

Mutationها فقط از پنل مدیریت پذیرفته می‌شوند. نمایشگر اجازهٔ استعلام state دارد ولی نمی‌تواند نتیجه یا قرعه را تغییر دهد. این جداسازی پنجره است، نه احراز هویت مستقل سرداور.

### سیاست انتشار و نوبت

- بنا به انتخاب کاربر، draftها فوراً در جدول زندهٔ سالن و آیتم‌ها مرتب می‌شوند و «موقت» برچسب دارند.
- `standings` و PDF رسمی همچنان فقط approvedها را شامل می‌شوند؛ `liveStandings` و `itemLeaderboards` شامل draft و approved هستند.
- بازکردن approved برای اصلاح، سهم رسمی را حذف می‌کند ولی رکورد در جدول موقت باقی می‌ماند؛ ذخیرهٔ اصلاح sort را فوراً تغییر می‌دهد.
- نوبت در `draw.entries[].drawOrder` ذخیره می‌شود، نه از rank استخراج؛ قرعهٔ آیتم بر عمومی اولویت دارد.
- پس از اولین نتیجهٔ محدوده، قرعهٔ همان محدوده ثابت است: `all` پس از هر نتیجه و قرعهٔ آیتم پس از نتیجهٔ همان آیتم قفل می‌شود؛ سایر آیتم‌های شروع‌نشده قابل قرعه‌اند.
- پیش از شروع، جایگزینی با تأیید UUID مجاز و تاریخچه محفوظ است. شماره صفر، اعشاری، تکراری، تیم ناشناخته و فهرست ناقص رد می‌شود.
- تیمی که بعد از قفل اضافه شود نوبت ساختگی نمی‌گیرد؛ `—` دیده می‌شود. فهرست تیم‌ها را پیش از قرعه نهایی کامل کنید.
- دادهٔ نسخه‌های ۱/۲ به نسخهٔ دادهٔ ۳ مهاجرت می‌کند؛ شماره‌های قدیمی از ترتیب ذخیره‌شده استخراج می‌شوند. پیش از ارتقا backup بگیرید.

### قوانین sort

علمی: نمره نزولی، سپس زمان پاسخ صعودی. ترکیبی: میانگین زمان دو نفر + جریمه صعودی. سایر رشته‌ها: زمان + جریمه صعودی. تساوی دقیق رتبه مشترک و جهش بعدی دارد (`1,1,3`). نوبت فقط ترتیب نمایش تیم‌های برابر/ثبت‌نشده را تثبیت می‌کند، **معیار شکستن تساوی رتبه نیست**. کل مسابقه جمع رتبه‌ها است و رتبهٔ کل تا تکمیل پنج آیتم null می‌ماند.

از نسخه ۱.۴.۲، زمان پنل و سالن با دو رقم صدم نمایش داده می‌شود. میانگین برای نمایش گرد می‌شود؛ مقدار دقیق میلی‌ثانیه و رتبه‌بندی بر اساس آن حفظ می‌شود. چیدمان ۱۱ تیم/۲۲ ورزشکار در هر صفحه یا همه در یک صفحه، در آزمایش واقعی ویندوز بررسی می‌شود.

## ۳. ساختار داده

[JSON Schema رسمی read-model](live-data.schema.json) و [نمونهٔ واقعی تولیدشده توسط smoke](../release/qa/live-data-example.json).

```json
{
  "team_id": 2,
  "draw_order": 13,
  "total_rank": 1,
  "official_total_rank": null,
  "item_scores": {
    "water": {
      "draw_order": 13,
      "rank": 1,
      "final_value": 20000,
      "raw_primary_ms": 20000,
      "raw_secondary_ms": null,
      "penalty_ms": 0,
      "scientific_duration_ms": null,
      "status": "draft",
      "unit": "ms"
    }
  }
}
```

بالا یک نمونهٔ مختصر از یک آیتم است؛ سند کامل schema حضور هر پنج آیتم را الزامی می‌داند. پوشش بیرونی: `{schema_version:3, revision, team_scores:[...]}`. `total_rank` رتبهٔ زنده است و `official_total_rank` فقط تأییدشده. این projection به‌صورت `view().team_scores` تولید می‌شود؛ منبع ذخیرهٔ اصلی همچنان teams/results/draws است تا رتبهٔ ذخیره‌شدهٔ کهنه ایجاد نشود. `null` یعنی ثبت‌نشده/تکمیل‌نشده؛ صفر رتبه یا نوبت معتبر نیست. همهٔ زمان‌ها میلی‌ثانیه‌اند و scientific با points مشخص است.

## ۴. چک‌لیست قابل تکرار

### آزمون خودکار

از پوشهٔ پروژه:

```bash
npm test
npm run test:smoke
```

پروژه TypeScript/typecheck ندارد؛ `node --check` بررسی syntax است، نه بررسی نوع. smoke بومی از پنل و IPC production با دادهٔ موقت استفاده می‌کند و خروجی در `release/qa` می‌سازد؛ دادهٔ واقعی مسابقه دست‌نخورده می‌ماند. در لاگ، خطای عمدی «عملیات فقط از پنل مدیریت مجاز است» آزمون مثبت محدودیت دسترسی است؛ exit نهایی معیار موفقیت است.

### نوبت دستی و ذخیره

- [ ] پیش از ثبت نتیجه، سه تیم الف/ب/ج بسازید؛ نوبت‌های ۳/۱/۲ وارد کنید.
- [ ] ثبت دستی را بزنید؛ ترتیب قرعه باید ب/ج/الف باشد.
- [ ] نوبت تکراری، خالی، صفر و اعشاری را امتحان کنید؛ state و قرعه نباید تغییر کنند.
- [ ] برنامه را ببندید و باز کنید؛ شماره‌ها و قرعهٔ انتخاب‌شده باید همان بمانند.
- [ ] یک نتیجهٔ آیتم ثبت کنید؛ تغییر قرعهٔ عمومی و همان آیتم باید رد شود.
- [ ] یک رشتهٔ دیگرِ شروع‌نشده را قرعه بزنید؛ قرعهٔ مستقل آن باید حفظ شود.

### مانیتور دوم

- [ ] کابل ویدئوال را وصل و Win+P → Extend را انتخاب کنید؛ در تنظیمات، مانیتور مقصد را ببینید.
- [ ] Extend و مقصد سالن را انتخاب و بازکردن را بزنید؛ صفحه سالن باید روی مقصد تمام‌صفحه باشد.
- [ ] بازکردن دوباره نباید پنجرهٔ اضافی بسازد.
- [ ] Mirror را امتحان کنید؛ همان تابلوی عمومی باید به‌صورت پیش‌نمایش روی اصلی باشد، نه پنل اپراتور.
- [ ] بستن و بازکردن، و reload صفحه باید آخرین state/آیتم را بازیابی کند.
- [ ] قطع کابل باید صفحه را به مانیتور موجود منتقل کند؛ اتصال مجدد در انتخاب خودکار باید مقصد دوم را انتخاب کند.
- [ ] خطای load باید پیام خطا بدهد، نه اعلان موفقیت جعلی.

### تغییر آنی رتبهٔ هر آیتم

- [ ] از «تابلوی نتایج → صفحه سالن»، آبرسانی را انتخاب و منتشر کنید.
- [ ] زمان الف ۳۰ و ب ۴۰ ثانیه ثبت کنید؛ بدون تأیید، الف اول و ب دوم، هر دو موقت باشند.
- [ ] زمان ب را ۲۰ ثانیه کنید؛ ب فوراً اول شود و ردیف جابه‌جا‌شده هایلایت شود.
- [ ] شماره نوبتِ هر دو در تمام مراحل ثابت بماند؛ برچسب آبی با رتبهٔ طلایی جدا باشد.
- [ ] تأیید ب وضعیت را رسمی کند؛ بازکردن آن وضعیت را موقت کند و امکان اصلاح با دادهٔ پیش‌پر بدهد.
- [ ] علمی را با نمره ۸۰/۹۵ امتحان کنید؛ بالاتر اول باشد؛ نمرهٔ مساوی با زمان متفاوت درست sort شود.
- [ ] ترکیبی را با ۶۰ و ۸۰ ثانیه و جریمهٔ ۵ ثبت کنید؛ زمان نهایی ۷۵ ثانیه باشد.
- [ ] هر پنج صفحهٔ آیتم، کل مسابقات و قرعه را عوض کنید؛ state انتخاب‌شده پس از reopen محفوظ باشد.
- [ ] حداقل ۱۴ تیم برای صفحه‌بندی آزمایش کنید؛ دکمه قبل/بعد، توقف/ادامه، تنظیم گردش و گردش ده‌ثانیه‌ای درست باشند.
- [ ] کاهش حرکت سیستم باید حرکت و گردش خودکار را متوقف کند؛ page navigation دستی فعال بماند.
- [ ] PDF رسمی draft را حساب نکند؛ PDF قرعه شماره‌های نوبت ثابت را چاپ کند.

## ۵. نتیجهٔ بررسی و محدودیت

نتایج نهایی اجرا در [smoke-result.json](../release/qa/smoke-result.json) هستند: **۲۱ آزمون واحد و ۱۱ سناریوی بومی Electron موفق شدند**. syntax تمام فایل‌های اجرایی/آزمون و `git diff --check` موفق بود. JSON Schema با validator استاندارد draft 2020-12 و نمونهٔ واقعی هر ۱۴ تیم اعتبارسنجی شد. در اجرای نهایی، ویرایش آبرسانی تا مشاهدهٔ رتبهٔ جدید ۱۶ میلی‌ثانیه اندازه‌گیری شد.

در توسعهٔ smoke، اجرای اولیه به‌علت capture از پنجرهٔ پنهان متوقف شد و probe با selector عددی نامعتبر شکست خورد؛ harness اصلاح و اجرای کامل دوباره انجام شد. assertionها حذف یا ضعیف نشدند. mirror بسته‌های Python برای validator timeout داشت؛ نصب محلی از PyPI اصلی موفق شد. در وضعیت نهایی هیچ بررسی ضروریِ ناموفق یا درحال‌اجرا باقی نمانده است. در آزمون بومی با ۱۴ تیم، زمان یک ویرایش تا ظاهرشدن رتبه روی renderer اندازه‌گیری شده و در `timings` ذخیره شده است؛ این یک نمونهٔ محلی است، نه تضمین SLA یا ادعای سرعت نسبت به نسخهٔ قبل.

آزمون topology و load-failure با doubles قابل‌کنترل و lifecycle/IPC/رابط/PDF با Electron واقعی بررسی می‌شود. ویدئوال فیزیکی، HDMI، DPIهای مختلف، شنیدن صوت و قطعی برق هنوز نیاز به تمرین سالن دارند. این تغییرات در commit نسخهٔ ۱.۲.۰ به شاخهٔ `main` منتشر شده و با تگ `imidro-fire-v1.2.0` در Release رسمی قرار می‌گیرد. راهنمای PDF ضمیمهٔ Release همچنان محتوای نسخهٔ ۱.۱ را دارد و به‌روزرسانی آن به مرحلهٔ بعد موکول شده است.
