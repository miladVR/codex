# راهنمای استفاده از Spec Kit و Codex در مخزن miladVR/codex

این راهنما برای توسعه مبتنی بر مشخصات (Spec-Driven Development یا SDD) در مخزن چندپروژه‌ای `miladVR/codex` است. فایل‌های رسمی Spec Kit 1.3.2 از طریق GitHub Actions تولید شده و با اتصال `codex` ثبت شده‌اند. نصب خود برنامه Codex CLI روی رایانه کاربر جزئی از این راه‌اندازی مخزن نیست.

## چه چیزهایی اضافه شده است؟

- `.specify/`: قالب‌ها، اسکریپت‌های PowerShell، اطلاعات اتصال، گردش‌کارها و سند اصول توسعه.
- `.agents/skills/speckit-*/SKILL.md`: ۹ مهارت رسمی قابل فراخوانی در Codex.
- `AGENTS.md`: راهنمای عامل برنامه‌نویس برای رعایت محدوده پروژه، تست و کنترل انتشار.
- `.specify/memory/constitution.md`: اصول پیشنهادی توسعه این مخزن.

**نکته:** تا زمان تأیید و ادغام Pull Request، این تغییرات فقط در شاخه آزمایشی قرار دارند و روی `main` یا نسخه نصب‌شده مسابقات اثری ندارند.

## شروع کار در ویندوز

در PowerShell، پس از نصب Git، Python 3.11 یا بالاتر، `uv` و Codex CLI، این دستورها را اجرا کنید:

```powershell
git clone https://github.com/miladVR/codex.git
cd codex
git switch chore/spec-kit-codex-bootstrap

# برای مدیریت CLI و ارتقای بعدی؛ چارچوب پروژه از قبل ساخته شده است.
uv tool install specify-cli==1.3.2
specify version
specify integration status

# اجرای Codex از ریشه مخزن
codex
```

اگر مخزن را قبلاً دریافت کرده‌اید، به‌جای `git clone` از `git fetch` و سپس `git switch chore/spec-kit-codex-bootstrap` استفاده کنید. پس از ادغام PR، دیگر نیازی به شاخه آزمایشی نیست و می‌توانید از `main` به‌روز استفاده کنید. **دستور `specify init` را دوباره اجرا نکنید** مگر برای ترمیم یا ارتقای هدفمند فایل‌های اولیه.

## آغاز اولین قابلیت با مشخصات

دستورهای زیر باید **در گفت‌وگوی Codex** اجرا شوند، نه در ترمینال PowerShell:

1. `$speckit-specify` — توضیح ویژگی و معیارهای پذیرش؛ حتماً مسیر پروژه هدف را نام ببرید.
2. `$speckit-clarify` — شناسایی ابهام‌ها و رفع فقط موارد مؤثر بر نتیجه.
3. `$speckit-plan` — برنامه فنی مبتنی بر معماری فعلی و خطرهای تغییر.
4. `$speckit-tasks` — شکستن برنامه به کارهای قابل اجرا و آزمون.
5. `$speckit-analyze` — کنترل سازگاری مشخصات، برنامه و وظایف.
6. `$speckit-implement` — پیاده‌سازی محدود و آزمون مرحله‌ای.
7. `$speckit-converge` — مقایسه خروجی واقعی با معیارهای پذیرش و ثبت موارد باقی‌مانده.

مهارت `$speckit-constitution` برای ایجاد یا بازنگری اصول پروژه استفاده می‌شود؛ پیش‌نویس این اصول از قبل در `.specify/memory/constitution.md` آماده شده است.

## پروژه اول: سامانه امتیازدهی آتش‌نشانان ایمیدرو

**مسیر:** `imidro-fire-scoreboard/` — نرم‌افزار Electron برای ویندوز و استفاده آفلاین.

در درخواست توسعه، صریحاً بنویسید که نباید داده مسابقه، قواعد محاسبه امتیاز و رتبه، تأیید سرداور، نسخه پشتیبان و فرآیند نصب نسخه موجود آسیب ببینند. برای تست‌های اصلی:

```powershell
cd imidro-fire-scoreboard
npm ci
npm test
```

برای تست تعاملی با دسترسی به Electron و محیط گرافیکی:

```powershell
npm run test:smoke
```

تست نصب‌کننده واقعی در ویندوز، مانیتور دوم و PDFها باید جداگانه ثبت شود. اجرای `npm test` به‌تنهایی این موارد را تأیید نمی‌کند.

## پروژه دوم: Cloze Studio

**مسیر:** `cloze-studio/` — ابزار تحت مرورگر با خروجی چاپی و رابط فارسی/انگلیسی.

```powershell
cd cloze-studio
npm test
npm run check
```

در تغییرات رابط، استفاده آفلاین، نمایش راست‌به‌چپ، پنج نوع سؤال و قالب‌های چاپ حفظ شوند.

## الگوی کوتاه درخواست به Codex

> در پوشه `imidro-fire-scoreboard` فقط [ویژگی موردنظر] را بررسی کن. ابتدا با Spec Kit مشخصات و معیارهای پذیرش بنویس؛ سپس برنامه، وظایف، ریسک‌های سازگاری و آزمون‌های لازم را آماده کن. بدون تأیید مشخصات، هیچ تغییر عملیاتی، انتشار، ادغام یا حذف داده‌ای انجام نده. پس از پیاده‌سازی، تست‌های واقعاً اجراشده و موارد بررسی‌نشده را شفاف گزارش کن.

## سیاست ایمنی و انتشار

این راه‌اندازی فقط مسیر توسعه را ساختاربندی می‌کند؛ خودبه‌خود هیچ ویژگی جدیدی به برنامه اضافه یا منتشر نمی‌کند. تغییرات آینده باید در شاخه جدا، با بازبینی مستقل و آزمون، از طریق PR پیشنهاد شوند. انتشار Setup یا نسخه پرتابل، تغییر `main` و عملیات حساس نیازمند تأیید صریح است.
